| 15 | Kalshi fetch failure reported as success, and empty-fetch retirement | `kalshi-fetch-failure` | shipped | PR [#16](https://github.com/samuellittlefield/News-Site-Aggregator/pull/16). Fragility fix, not a live-outage response — Kalshi recovered on its own within the hour of the 2026-09-12 incident, so reproduced with a mocked 403 rather than chasing the connectivity issue. Two defects fixed: (1) `fetch_kalshi` now tracks per-series outcomes in `series_errors`; if *every* series fails (request error, non-2xx, or an unparseable/unexpected body) it raises, so the scheduler wrapper's existing `except` records a real `SourceRun` **failure** with the upstream error, instead of a clean return read as `success`/`item_count: 0`. A partial failure (one series up, one down) still saves what it got and returns normally. (2) The retirement query's `notin_(seen_ids)` against an empty set excluded nothing and flipped every stored Kalshi market inactive on any run that found nothing — guarded on non-empty `seen_ids`, plus scoped to only the series actually fetched this run (market ids are always `"<SERIES_TICKER>-..."`), since on a partial failure `seen_ids` only contains the healthy series' tickers and an unscoped guard would still retire the *down* series' existing markets. A real disappearance within a successfully-fetched series still retires normally (TC-4, unbroken). Deliberately untouched: `MIN_VOLUME_24H` and the series tickers (live volume was 163k-178k, well over the 1000 floor), the in-house forecast model, and the connection itself (no header/host change — `api.elections.kalshi.com` returns `yes_bid`/`last_price` as null where `external-api` returns populated `*_dollars` fields, not a drop-in).
