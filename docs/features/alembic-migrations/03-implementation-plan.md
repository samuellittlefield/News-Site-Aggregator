**Slug:** `alembic-migrations` &nbsp; **Source:** `01-feature-plan.md`, `02-acceptance-criteria.md`

Generate a hand-reviewed baseline migration from the current models, stamp the existing prod DB, run `alembic upgrade head` ahead of uvicorn in the Procfile, and retire `create_all` as the schema authority after one safety release.

## Data Model / Migration Notes
- Baseline is schema-only, no data movement.
- **One-time ops step (manual, before merging the Procfile change):** run `alembic stamp head` against prod — otherwise the first deploy tries to re-create every table and fails. Sequence matters; see below.
- Before stamping, run `alembic revision --autogenerate` pointed at prod (read-only check) to detect latent drift between prod schema and models. Any drift → reviewed revision 002.

## Sequencing
1. `env.py` URL rewrite (safe, standalone)
2. Generate baseline against a fresh local DB; verify AC-1 (upgrade → empty autogenerate diff); commit
3. Drift check against prod (read-only autogenerate diff); fold any findings into revision 002
4. **Ops:** `alembic stamp head` on prod
5. Merge Procfile change (deploys now run `upgrade head` — a no-op until the next real migration)
6. Docs + template updates
7. Follow-up release: remove `create_all` from `lifespan`

## Risks / Rollback
- **Stamp-before-Procfile ordering**: if the Procfile lands before prod is stamped, the deploy fails on "table already exists." Mitigation: sequencing above; rollback is reverting the Procfile line (app still boots via `create_all` during release-1 window).
- **Autogenerate fidelity on JSONB/defaults**: mitigated by hand review (AC-1's empty-diff check is the proof).
- **Bad future migration blocks deploys**: intended behavior; rollback path is `alembic downgrade -1` + revert, or hotfix migration.
- **Concurrent migrators**: not a concern on single-instance Railway; revisit if scaling out.
