# Feature Plan: Adopt Alembic Migrations

**Slug:** `alembic-migrations` &nbsp; **Owner:** Samuel &nbsp; **Status:** Approved — ready for implementation &nbsp; **Date:** 2026-07-02

## Problem / Goal
Alembic is installed and fully configured (`alembic.ini`, `env.py` wired to `Base.metadata` and `DATABASE_URL`) but `alembic/versions/` is empty — the schema has only ever been managed by `Base.metadata.create_all()` in `lifespan`. `create_all` creates missing tables but never alters existing ones: add a column to a model and the production Postgres on Railway silently won't have it until a query 500s at runtime. Goal: baseline the current schema as migration 001, switch deploys to `alembic upgrade head`, and make "generate a migration" a standard step in every future feature that touches `models.py`.

## Context
- Cross-cutting infrastructure — every ingestion domain in `SOURCES.md` writes to tables this governs (~23 models in `backend/app/models.py`).
- Builds on the existing (dormant) Alembic setup: `backend/alembic.ini`, `backend/alembic/env.py` (already reads `DATABASE_URL` from env, `target_metadata = Base.metadata` already set).
- Why now: the schema has grown to ~23 tables through Phase F model work, FEC candidates, retirements, etc., all deployed by luck of "new tables only." The next feature that *alters* a table breaks prod. The implementation-plan template already says "models.py + Alembic migration" — the machinery just doesn't exist.

## Scope
- [x] Baseline migration: autogenerated revision 001 capturing the full current schema
- [x] Deploy path: run `alembic upgrade head` on Railway before app start (Procfile or startup hook), replacing `create_all` as the schema authority
- [x] Existing prod DB handling: one-time `alembic stamp head` so the baseline isn't re-applied to a database that already has the tables
- [x] Local dev path: documented flow — `alembic upgrade head` after pull, `alembic revision --autogenerate` when changing models
- [x] Pipeline convention: implementation-plan template gains an explicit "migration generated? y/n" checklist line

## Non-Goals
- Data migrations / backfills (baseline is schema-only)
- Tested downgrade paths (write them, don't guarantee them)
- Squashing or history hygiene policies — irrelevant until there's history
- Removing `create_all` from test fixtures (the `test-harness-ci` feature intentionally keeps it there for speed)

## Proposed Approach
1. **Generate baseline**: against a fresh local DB, `alembic revision --autogenerate -m "baseline"` and hand-review the output — autogenerate misses server-side defaults and can mis-render `JSONB` defaults (`sources_list`, etc.). The reviewed 001 becomes the schema of record.
2. **Stamp existing DBs**: prod (and any long-lived local DB) gets `alembic stamp head` once, marking the baseline as already applied. Fresh DBs run `upgrade head` and get everything.
3. **Wire into deploy**: change `backend/Procfile` to run migrations before uvicorn (`web: alembic upgrade head && uvicorn app.main:app ...`) — Railway has no separate release phase, so this is the reliable hook. Keep `create_all` in `lifespan` for one release as a safety net, then remove it so Alembic is the single authority.
4. **Document the loop**: short section in `SOURCES.md` or a `backend/README` snippet — model change → autogenerate → review → commit migration alongside the model change, same PR.
5. **Update pipeline template**: `03-implementation-plan.md` template gets a migration checklist line so every future feature that touches `models.py` ships its migration.

## Open Questions / Risks
- **Autogenerate fidelity**: first diff against prod may reveal drift (columns that exist in models but were added after a table already existed — i.e. bugs this feature exists to prevent may already be latent). Plan: run a schema diff against prod before stamping; any drift becomes revision 002.
- **Startup ordering**: `upgrade head` in the Procfile runs on every deploy — fine, it's idempotent. But a failed migration now blocks deploys (that's the correct behavior; just be aware the failure mode moves from "silent drift" to "loud deploy failure").
- **Interaction with `test-harness-ci`**: none in v1 (tests keep `create_all`), but CI could later add an "autogenerate produces empty diff" check to catch model/migration drift — noted as a future stage-4 candidate.
- Multiple app instances migrating concurrently isn't a concern on Railway's single-instance setup today; revisit if scaling out.
